# LineSim

เปิด `index.html` ในเบราว์เซอร์ได้โดยตรง สำหรับใช้ GPU บน Debian เครื่องนี้ ให้เปิดผ่าน:

```sh
./run-gpu.sh
```

ตัวเปิดใช้ Chrome profile แยกที่ `~/.cache/linesim-chrome-gpu` ไม่แก้ profile หลัก และเปิด Vulkan/WebGPU ตาม[แนวทางของ Chrome](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips) หน้าจอจะแสดง `GPU amd · ตารางเซนเซอร์พร้อม` เมื่อใช้ AMD GPU ได้จริง หากไม่มี adapter จะเตรียมตารางเซนเซอร์ด้วย CPU แทน และแจ้งตามจริง ไม่กลับไปอ่านพื้นที่รับแสงซ้ำ 5 ครั้งในทุกสเต็ป

## เซนเซอร์และ GPU

ตัวจำลองไม่เติม noise สุ่ม ไม่มีพารามิเตอร์หรือช่องปรับ noise ทั้งในรอบจำลองและบันทึก/เล่นซ้ำ ข้อมูลจริงจากหุ่นยังคงเดิม

ตรวจซอร์ส `getCalibratedValue()` / `calPoint()` ใน ซอร์สไลบรารีเซนเซอร์ 16 ช่อง (ไม่เผยแพร่) แล้ว: ไลบรารีปรับช่วง White/Black และใช้ deadband `difWhite=20`, `difBlack=10` ก่อนหาตำแหน่งแบบ weighted average ตัวจำลองใช้สัญญาณอุดมคติหลังตั้งค่าแสงตามคำขอ จึงไม่เติม Gaussian noise ทับค่าสัญญาณนี้ ไม่ได้ยืนยันว่าฮาร์ดแวร์จริงไม่มีสัญญาณรบกวนทุกกรณี

การตรวจ 12 ครั้งใช้ตำแหน่งเริ่มต่างกันตามแนวขวาง -0.5 ถึง +0.5 ซม. รวมมุมเริ่ม +1° ไม่มีการอ้างว่าเป็นการสุ่ม noise 12 ชุด

GPU ใช้ compute shader เตรียมตารางพื้นที่รับแสงของเซนเซอร์ 2,430,000 จุดต่อสนาม จากนั้น CPU workers ทุกเธรดที่เบราว์เซอร์เปิดให้ใช้ตารางนี้อ่านเซนเซอร์ระหว่างค้นค่าจูน ตารางถูกแคชแยกตามสนาม และคืน GPU buffers/device หลังเตรียมเสร็จ จึงไม่ได้รัน GPU เต็มเวลาตลอดการจูนหรือย้าย PID/ฟิสิกส์ทั้งหมดไป GPU

ตาราง GPU ใช้ f32 แต่ PID/ฟิสิกส์ยังใช้ JavaScript f64 ใกล้ขอบสนามหรือค่าที่อาจทำให้การปัดค่าเซนเซอร์เปลี่ยน จะกลับไปคำนวณสูตรเดิม เทียบการอ่าน 50,000 ตำแหน่งแล้วค่าเซนเซอร์เต็มจำนวนตรงกับ CPU ทุกตำแหน่ง และทดสอบประวัติการวิ่งทั้งรอบให้ตรงกันทุกสเต็ป

ผลวัดก่อนเพิ่มดัชนีเส้นทาง ที่ Best speed 90 บน AMD GPU + Ryzen 5 5625U ในรอบทดสอบที่ไม่มีงานทดสอบอื่นรันคู่กัน: CPU 12 workers 2.779 วิ, GPU-assisted CPU 12 workers 2.354 วิ (ไม่รวมการเตรียมตารางครั้งแรกประมาณ 81 ms) ค่าจูนและคะแนนตรงกัน ใช้ตาราง GPU ใน workers ประมาณ 51.5 ล้านครั้ง เวลาอาจต่างกันตามโหลดเครื่อง สนาม และ driver

## เกณฑ์การจูน

ใช้เกณฑ์ **หลุดแนวน้อย ตามโค้งต่อเนื่อง และทำเวลาต่อรอบได้เร็ว** ค้นหา Kp, Kd และ slowrage ร่วมกัน แล้วค้นละเอียดรอบชุดที่มีแนวโน้มดี การจบครบ 12 จุดเริ่มใช้ตรวจความสม่ำเสมอ ส่วนการจัดอันดับใช้คุณภาพการตามเส้นร่วมกับเวลา

- **Best (ตามเส้น + เวลา)** คง speed ที่ผู้ใช้ตั้งไว้
- **เร็วสุด (ตามเส้นต่อเนื่อง)** ค้น speed 30–250 ทีละ 10 รวม 255 และ speed ปัจจุบัน จากนั้นค้นเพิ่ม -10, -5, 0, +5, +10 รอบชุดที่มีแนวโน้มดี 24 ชุด ตรวจผู้เข้ารอบสูงสุด 96 ชุด ไม่หยุดเมื่อพบเพียงค่า PWM สูงที่วิ่งจบ

วัดการเยื้องแนวจากระยะแถวเซนเซอร์ถึงเส้นทางอ้างอิงเกิน 2 ซม. แยกเวลารวม ช่วงต่อเนื่องยาวสุด และส่วนที่อยู่ในโค้ง โค้งอ้างอิงจากรูปทรงเส้นทาง การเยื้องแนว 2 ซม. เป็นเพียงตัวช่วยจัดตำแหน่งที่มีน้ำหนักเบา ไม่ใช้แทนการหลุดเส้น หากเซนเซอร์ยังเห็นเส้นจะไม่นับเป็นช่วงขาดการตามเส้นในโค้ง เซนเซอร์ไม่เห็นเส้นวัดจากค่าอ่านเป็นศูนย์ทั้งแถวและรายงานแยกกัน

คะแนนต่อการวิ่ง (ต่ำดีกว่า หน่วยต้นทุนเทียบวินาที) = เวลารอบ + 0.1×เวลาเยื้องแนวเกิน 2 ซม. + 0.2×เวลาเยื้องแนวในโค้ง + 4×เวลาที่เซนเซอร์ไม่เห็นเส้น + 6×เวลาที่เซนเซอร์ไม่เห็นเส้นในโค้ง + 6×ช่วงไม่เห็นเส้นต่อเนื่องยาวสุด + 8×ช่วงไม่เห็นเส้นในโค้งต่อเนื่องยาวสุด + 0.25×ระยะห่างโค้ง RMS (ซม.) รวมข้ามการทดสอบด้วยค่าเฉลี่ย 75% และรอบที่คะแนนแย่สุด 25% คัดชุดที่จบครบ 12 ครั้งก่อน แล้วเลือกคะแนนต่ำสุด ตัวคูณเป็นค่าตั้งต้นของตัวจูน การเบี่ยงเซนเซอร์ออกจากกึ่งกลางเส้นขณะเข้าโค้งตามปกติไม่ถือว่าเป็นการหลุดเส้น

การเลือกเป็นการแลกคุณภาพบางด้านกับเวลา ไม่รับประกันว่าดีขึ้นทุกตัวชี้วัดหรือเป็นค่าที่เหมาะสมที่สุดทุกค่าที่เป็นไปได้ ระยะเวลาจำลองใช้ค่าที่ตั้งในหน้าจอ หากไม่มีชุดผ่านครบ จะแสดงผลบางส่วนและระบุว่ายังไม่ผ่านเกณฑ์ ผลทั้งหมดเป็นของโมเดลจำลอง ยังไม่ยืนยันกับหุ่นจริง

## ทดสอบ

ใช้ Node.js และ Google Chrome บน Linux:

```sh
npm install
npm test
npm run test:workers
npm run test:objective
npm run test:gpu
npm run bench
npm run test:optimization
```

ตั้ง `CHROME_PATH` หาก Chrome อยู่คนละตำแหน่ง ค่าเริ่มต้นคือ `/usr/bin/google-chrome` การทดสอบ GPU ต้องเข้าถึง hardware adapter ได้ ส่วนการทดสอบทั่วไปตรวจทาง CPU fallback ด้วย

- `test`: กด Best ในเบราว์เซอร์ ตรวจรอบที่แสดง 12 จุดเริ่ม การคืนค่า แคช และยกเลิกงานที่กำลังทำ
- `test:workers`: เปิดจากไฟล์ ตรวจทุก worker ได้คำนวณและคืนครบ ทดสอบโหมดเร็วสุด และการคำนวณต่อเมื่อ worker ล้มเหลว
- `test:objective`: ตรวจการให้คะแนนสามเกณฑ์ และผลเลือกชุดค่าจูนในสนาม Senior
- `test:gpu`: ใช้ hardware GPU ตรวจ 50,000 ค่า ประวัติการวิ่งทั้งรอบ ผลจูนเทียบ CPU การใช้ตารางใน workers และการเปลี่ยนสนาม
- `bench`: เทียบเธรดเดียวกับทุก CPU workers โดยใช้เกณฑ์เดียวกัน ผลต้องตรงกัน

ไฟล์ก่อนเปลี่ยนแต่ละช่วงอยู่ใน `.backups/` ข้อมูลผลวัดก่อนเอา noise ออกอยู่ใน `README-before-noise-gpu-20261112.md` ภายใต้โฟลเดอร์นั้น ใช้เป็นประวัติ ไม่ใช้เทียบผลวิ่งกับโมเดลปัจจุบันโดยตรง

## ลดงานค้นเส้นทางและการจำลองซ้ำ

การตรวจเส้นทางเดิมไล่เทียบจุดได้ถึง 281 จุดทุกสเต็ป PID รุ่นปัจจุบันใช้ต้นไม้กรอบขอบเขตของเส้นทางเพื่อข้ามกลุ่มจุดที่ไม่มีทางใกล้กว่าจุดที่พบแล้ว ยังค้นในช่วงดัชนีเดิม และเลือกดัชนีต่ำกว่าเมื่อระยะเท่ากัน ไม่ใช้การประมาณเส้นทาง การตรวจ 32,000 ตำแหน่งครอบคลุมทั้ง 5 สนามต้องได้จุดและระยะตรงกับการไล่เทียบเดิมทุกค่า

รอบยืนยัน 12 จุดเริ่มนำผล 3 จุดที่เคยคำนวณตอนคัดกรองกลับมาใช้ โดยเก็บค่าต่อการวิ่งและบวกตามลำดับเดิม ไม่สร้างผลซ้ำขึ้นมาและไม่ลดจำนวนจุดเริ่มที่ตรวจ ไม่ลดจำนวนชุดค่าจูนหรือความละเอียดของกริด

ผลวัดโหมดเร็วสุดใน Senior บน GPU+CPU 12 workers: ก่อนปรับ 11.315 วิ หลังปรับ 6.292 วิ เร็วขึ้นประมาณ 1.80 เท่าในรอบนี้ ผลค่าจูน คะแนนทุกค่า และประวัติการวิ่งตรงกัน ไฟล์ก่อนปรับอยู่ใน `.backups/index-before-route-index-20261112.html` และตรวจซ้ำได้ด้วย `npm run test:optimization`

Best แบบ GPU-assisted ในรอบทดสอบหลังปรับใช้ 1.429 วิ (CPU 12 workers อย่างเดียว 1.961 วิ) ส่วนผลการทดสอบกรณี workers ล้มเหลวระหว่างยืนยันผลตรวจให้ทางสำรอง CPU นำข้อมูลคัดกรองที่แคชไว้มาคำนวณต่อ และได้ชุดจูนเดิมครบ 12 จุดเริ่ม

ทางสำรองเมื่อ GPU ไม่พร้อมใช้ตารางที่เตรียมด้วย CPU เช่นกัน ตรวจแล้วประวัติการวิ่งและค่าจูนตรงกับสูตรเดิม โหมดเร็วสุดจากการเปิดไฟล์ใน Chrome ปกติใช้ประมาณ 6.486 วิในรอบทดสอบนี้ โดยไม่ต้องเปิด GPU ก่อน

## ฟิสิกส์และจุดอ้างอิงจากหุ่นจริง

เปลี่ยนแกนกลศาสตร์ร่วมทั้ง simulation, auto tune, record/replay และ reconstruction เป็นแรงมอเตอร์ DC/แรงบิด/ความเฉื่อย, น้ำหนักกดล้อขณะเร่ง, วงแรงเสียดทานร่วมสำหรับเร่งกับเลี้ยว, contact impulse สำหรับการไถล, แรงต้านการกลิ้ง และโมเมนต์หน้ายก/ตกกลับด้วยแรงโน้มถ่วง เซนเซอร์ลดสัญญาณตามความสูง ถอดความหน่วงเร่ง/เลี้ยวแบบเดิมกับ timer ดับเซนเซอร์ออก

อ่าน [MODEL_NOTES.md](MODEL_NOTES.md) สำหรับสมการ ค่าตั้งต้น และข้อจำกัด จุดศูนย์ถ่วง/ความเฉื่อย/แรงพัดลม/การรับแสงยังเป็นค่าที่ต้องวัดจากหุ่นจริง ปรับได้ในสภาพหุ่น และเปลี่ยนค่าแล้วคำนวณใหม่ครบทั้งรัน/ค้นค่าจูน

ค่าอ้างอิง `ATrack(100,.08,0,.004,-255,0,3500)` และ `ATrack(80,.08,0,.0024,-255,0,4500)` ผ่าน Formula μ=3 ครบ 12/12 จุดเริ่มโดยไม่มีช่วงเซนเซอร์ไม่เห็นเส้นในโมเดลใหม่ ตรวจทั้งช่วงคำสั่ง 3.5/4.5 วินาทีจากจุดเริ่มสนามด้วย ผลนี้ไม่ได้ยืนยันความเร็ว/trajectory ของหุ่นจริงตรงกันแล้ว

AccelSet ตั้งร่วมในแผงจูน ใช้ทุกโหมด ตั้งต้น (.17,80), rate=0 ปิด จำกัดเฉพาะออกตัวจนถึง speed แรก แล้วคำสั่งต่อเนื่องเปลี่ยนเป้าได้ทันที ตาม Pro 2.0.1 เวลา PID รอบแรกใช้ช่วงรอก่อนเริ่ม ตั้งต้น 500 ms ตาม examples; รอบต่อไป 5 ms

เมื่อเปลี่ยนยางหรือค่าฟิสิกส์จะแสดงสถานะคำนวณใหม่ ผลไม่ครบ 12 ครั้งไม่เก็บเป็นผลสำเร็จและไม่เขียนทับค่าจูนเดิมอัตโนมัติ ปุ่ม Best/เร็วสุดที่เลือกอยู่กดซ้ำเพื่อคำนวณใหม่ได้ การใช้ผลสำเร็จจากแคชแจ้งชัดเจน

## ตรวจผล

`npm run test:physics` ตรวจข้อกำหนดทางกลศาสตร์; `npm run test:firmware-timing` ตรวจ ref ทั้งสองชุด; `npm run test:accel` ตรวจการไต่ความเร็ว; `npm test` และ `npm run test:grip` ตรวจการจูน/คำนวณใหม่; `npm run test:gpu` ตรวจ hardware GPU และความตรงกันกับ CPU; `npm run test:workers` ตรวจทุกเธรดและ Max; `npm run bench` วัดเวลาในสภาพเครื่องปัจจุบัน

ตัวเลข benchmark ในหัวข้อก่อนหน้าเป็นโมเดลก่อนเปลี่ยนฟิสิกส์ ไม่ใช้รับรองเวลาของแกนแรงชุดใหม่ ซอร์สก่อนเปลี่ยนเก็บที่ `.backups/index-before-full-physics-20261112.html`

ผล benchmark แกนแรงชุดใหม่บนเครื่องนี้ (Senior, Best speed90, ตารางเซนเซอร์พร้อม, ไม่มีงานทดสอบอื่นรันคู่): เธรดเดียว 6.724 วิ, CPU12workers 1.853 วิ หรือ 3.63 เท่า ค่าจูน/คะแนนตรงกันและจบ12/12; Maxจากการตรวจworkersอีกรอบประมาณ10.22วิ ตัวเลขขึ้นกับโหลดเครื่องและสนาม

## Record -> replay and tuned defaults (2026-11-13)
The default tune is the one used on the real robot: speed 90, Kp 0.15, Kd 0.003, AccelSet(0.17, 80), AReplay(0.75). The record -> replay mode runs the same logic as library version 2.0.2 (see MODEL_NOTES.md).
